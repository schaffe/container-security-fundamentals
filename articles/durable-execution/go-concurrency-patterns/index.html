Go Concurrency: Classic Patterns¶

Overview¶

Go's concurrency model — goroutines, channels, select, context — is small enough to learn in an afternoon and subtle enough to misuse for years. This article builds the mental model first, then walks the classic patterns every Go service ends up containing — worker pools, fan-in, pipelines, bounded parallelism, rate limiting, graceful shutdown — each with working code and the reasoning behind every line. It closes with the pitfalls that account for most concurrency bugs in the wild (nearly all of them are goroutine leaks or channel-close mistakes in disguise) and a set of common questions answered in plain language.

The connection to the rest of this section is direct: Temporal's server and its most-used SDK are written in Go, and a Temporal worker is a set of poller goroutines feeding task channels, bounded by a slot semaphore, shut down by a context — every pattern here is running in production inside a durable execution platform.

Key Insight¶

Nearly every Go concurrency problem is the same problem wearing different clothes: move values between goroutines through channels, bound how many goroutines run at once, and make sure every goroutine you start has a guaranteed way to exit. If you can write a worker pool with clean shutdown — workers exit when the input channel closes or the context is cancelled, the output channel closes exactly once, and nothing leaks — you can solve the fan-in, pipeline, rate-limiter, and bounded-parallelism variants by rearranging the same three moves.

The invariants matter as much as the code, and they're worth stating explicitly whenever you write or review this kind of code: "the channel is closed from the sender side, never the receiver," "wg.Add happens before the goroutine starts, not inside it," "this select exists so a worker doesn't block forever on a full output channel after cancellation." Code that can't articulate its invariants is code that loses them in the next refactor.

The Mental Model¶

Goroutines and channels¶

A goroutine is a function running concurrently with the rest of the program — started with the go keyword, scheduled by the Go runtime onto OS threads, and cheap enough (a few kilobytes of stack) that starting tens of thousands is normal. The catch is that goroutines are invisible: nothing tracks them for you, main exiting kills them all mid-flight, and a goroutine blocked forever on a channel nobody writes to is a leak — it holds its stack and everything it references until the process dies. A large share of writing correct concurrent Go is simply never creating one of those.

A channel is a typed conduit between goroutines: ch := make(chan int) creates one, ch <- v sends, v := <-ch receives. An unbuffered channel (capacity zero) makes send and receive a rendezvous — the sender blocks until a receiver is ready, and vice versa — which means a successful send is also a synchronization event: you know the other side has the value. A buffered channel (make(chan int, 8)) decouples the two sides up to its capacity; sends block only when the buffer is full. The useful framing: unbuffered channels transfer and synchronize; buffered channels are a queue with backpressure built in — when the buffer fills, producers slow to the consumers' pace automatically.

Closing a channel (close(ch)) is a broadcast that no more values are coming. Receivers can detect it — v, ok := <-ch returns ok == false on a closed, drained channel — and the for v := range ch loop exits automatically when the channel is closed and empty. The rules around close are rigid enough to be worth memorizing as a table:

Operation Nil channel Open channel Closed channel
Send ch <- v blocks forever blocks until received/buffered panics
Receive <-ch blocks forever blocks until sent returns remaining values, then zero value with ok == false
close(ch) panics closes it panics

Two design rules fall out of that table. First, only the sender closes a channel — the receiver can't know whether the sender is about to send, so a receiver-side close risks the send-on-closed panic. With multiple senders, no single sender can close either; you either let the channel be garbage-collected unclosed (fine — close is a signal, not a resource release) or have a coordinator close it after all senders finish, which is exactly what sync.WaitGroup + a closer goroutine does in the patterns below. Second, "blocks forever on nil" is a feature, not a trap: setting a channel variable to nil inside a select disables that case, which is the idiomatic way to switch a source off after it's drained.

select, context, and the synchronization toolbox¶

select waits on several channel operations at once and runs whichever becomes ready first (choosing randomly on ties — no priority). It's how Go expresses "this, or that, or give up": receive a result or notice a timeout or notice cancellation. A default case makes the whole thing non-blocking — try the send, and if nobody's ready, do something else — which is how you build "drop if full" semantics.

context.Context is Go's standard cancellation and deadline carrier. It flows as the first parameter through every call chain (func fetch(ctx context.Context, ...)); calling the cancel function returned by context.WithCancel — or a deadline expiring under context.WithTimeout — closes the channel returned by ctx.Done(), and everything blocked in a select with a case <-ctx.Done(): arm wakes up and unwinds. Cancellation in Go is cooperative: nothing kills a goroutine from outside; the goroutine must be written to observe Done() at every point where it blocks. "How do you stop a goroutine?" reduces to exactly that sentence.

The for/select loop: three shapes¶

In practice, "observe Done() at every blocking point" comes down to three loop shapes, and knowing which one a situation calls for is most of the skill.

Shape one: the event loop — a goroutine that consumes a channel until either the channel closes or the context is cancelled. A plain for v := range ch can't do this, because range watches exactly one thing: the channel. The moment a loop must watch two things — data and cancellation — range gets replaced by for + select:

for {
    select {
    case <-ctx.Done():
        return ctx.Err() // cancelled: report why
    case job, ok := <-jobs:
        if !ok {
            return nil // channel closed and drained: clean end of input
        }
        handle(job)
    }
}

The ok check is load-bearing. A receive on a closed channel doesn't block — it returns the zero value immediately, forever — so without ok this loop would spin at full CPU on zero-value jobs after the channel closes. And notice the two exits mean different things, so they return differently: cancellation is an abnormal end (ctx.Err() says whether it was cancel or deadline), close is the normal one.

Shape two: range with a cancellable send — the one used throughout the patterns below. When the receive side can rely on close alone, range stays; the select guards the send, which is the operation that can block indefinitely if the consumer went away:

for v := range in {
    select {
    case out <- transform(v):
    case <-ctx.Done():
        return
    }
}

The rule of thumb that picks between shapes one and two: wrap select around whichever operation can block with nobody on the other end. If that's the receive, use shape one; if it's the send, shape two; if both, shape one with the send also inside a select.

Shape three: the CPU-bound loop — no channels at all, just a long computation over a collection. Nothing here blocks, so nothing would ever notice Done() closing; the loop must poll for it explicitly, using ctx.Err() as a non-blocking check (it returns non-nil once the context is cancelled):

for i, item := range items {
    if i%1024 == 0 { // amortize the check on hot loops
        if err := ctx.Err(); err != nil {
            return err
        }
    }
    process(item)
}

One caveat spans all three shapes: select chooses randomly among ready cases, so if data is ready at the same moment cancellation fires, the loop may process another item or two before it notices Done(). Usually that's fine — cancellation is a request, not a guarantee of instantaneous stop. When it isn't fine (the next iteration is expensive or has side effects), check ctx.Err() at the top of the loop body so cancellation wins ties.

The sync package covers the cases channels handle awkwardly. sync.WaitGroup counts outstanding goroutines: Add(1) before starting each one, defer wg.Done() inside it, Wait() blocks until the count reaches zero. The classic mistake is calling Add inside the goroutine — Wait can then run before any Add has happened and return immediately; Add must happen-before the Wait it's meant to hold back, so it goes in the spawning goroutine. sync.Mutex protects shared state; sync.Once runs initialization exactly once under concurrent callers. The decision rule for mutex versus channel is about what you're modeling: channels for transferring ownership of data and signaling between goroutines; mutexes for guarding shared state in place (counters, caches, maps). A hit counter behind three channels is a design smell just as much as a hand-rolled queue built from a mutex and a slice.

One more tool earns its keep: golang.org/x/sync/errgroup. It's a WaitGroup that also collects the first error, cancels a shared context when any task fails, and — with SetLimit(n) — bounds concurrency. Several classic problems below collapse to five lines with it.

The Classic Patterns¶

Worker pool — the workhorse¶

The canonical problem: given a stream of jobs, process them with exactly N concurrent workers, deliver results, and shut down cleanly. Every requirement in that sentence maps to one piece of the solution.

func WorkerPool(ctx context.Context, jobs <-chan Job, workers int) <-chan Result {
    results := make(chan Result)
    var wg sync.WaitGroup

    for i := 0; i < workers; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for job := range jobs { // exits when jobs is closed and drained
                select {
                case results <- process(ctx, job):
                case <-ctx.Done(): // don't block forever if nobody's reading results
                    return
                }
            }
        }()
    }

    // Closer: the only goroutine allowed to close results, and only
    // after every sender (worker) has finished.
    go func() {
        wg.Wait()
        close(results)
    }()

    return results
}

Walking it invariant by invariant: concurrency is bounded by construction — N workers exist, so at most N jobs are in flight; no semaphore needed because the workers are the semaphore. Shutdown has two triggers and the code handles both: when the producer closes jobs, the range loop ends and workers drain what remains; when the context is cancelled, the select around the result send lets workers exit even if the consumer has stopped reading — omit that select and a cancelled consumer strands every worker blocked on results <-, one of the most common goroutine leaks in real codebases. Finally, results is closed exactly once, by a dedicated closer goroutine after wg.Wait(), honoring both close rules: sender-side close, coordinated across multiple senders.

The caller's side completes the picture: the producer writes jobs and — crucially — close(jobs) when done (sender closes); the consumer just ranges over results until it closes:

func main() {
    ctx, cancel := context.WithCancel(context.Background())
    defer cancel()

    jobs := make(chan Job)

    // Producer: feed the pool, then close — the close is what
    // eventually shuts the workers down and closes results.
    go func() {
        defer close(jobs)
        for _, j := range loadJobs() {
            select {
            case jobs <- j:
            case <-ctx.Done(): // stop feeding if we're cancelled
                return
            }
        }
    }()

    // Consumer: results closes only after all workers finish,
    // so this loop ends exactly when the work does.
    for res := range WorkerPool(ctx, jobs, 8) {
        if res.Err != nil {
            log.Printf("job %s failed: %v", res.ID, res.Err)
            continue
        }
        handle(res)
    }
}

Note the symmetry: the producer owns jobs and closes it; the pool owns results and closes it; the consumer closes nothing and simply ranges until the end. Each channel has exactly one closing party, and the shutdown sequence — producer finishes → workers drain → closer fires → consumer's loop ends — follows from the close rules alone, with no extra coordination. This shape — bounded workers pulling from a task channel, context-driven shutdown, a WaitGroup coordinating the close — is, not coincidentally, the skeleton of a Temporal worker: poller goroutines are the producers, the executor pool is the workers, and worker slots are the bound.

Fan-out / fan-in — merging channels¶

Fan-out is free in Go: multiple goroutines receiving from one channel automatically split the work, each value going to exactly one receiver. The interesting half is fan-in: merge many channels into one, closing the output only when every input is done.

func Merge[T any](ctx context.Context, inputs ...<-chan T) <-chan T {
    out := make(chan T)
    var wg sync.WaitGroup

    for _, in := range inputs {
        wg.Add(1)
        go func(in <-chan T) {
            defer wg.Done()
            for v := range in {
                select {
                case out <- v:
                case <-ctx.Done():
                    return
                }
            }
        }(in)
    }

    go func() {
        wg.Wait()
        close(out)
    }()
    return out
}

It's the worker pool with the roles inverted — one forwarding goroutine per input instead of N workers on one input — and the same two invariants carry it: every forwarder has a context escape hatch, and the single close happens after all senders finish. (Passing in as a parameter guards against the loop-variable capture bug; since Go 1.22 each iteration gets a fresh variable and the closure alone would be safe, but the explicit parameter is version-proof.)

Pipeline — stages connected by channels¶

A pipeline chains stages, each a goroutine (or pool) reading an input channel and writing an output channel. The pattern per stage is mechanical: create the output, launch the work, close the output when the input is exhausted, and give every send a cancellation escape.

func Stage[In, Out any](ctx context.Context, in <-chan In, f func(In) Out) <-chan Out {
    out := make(chan Out)
    go func() {
        defer close(out) // this stage is the sole sender: it closes
        for v := range in {
            select {
            case out <- f(v):
            case <-ctx.Done():
                return
            }
        }
    }()
    return out
}

Two properties are worth noting. Closing propagates forward on its own: the source closes its output, each stage's range ends, its defer close fires, and the shutdown ripples to the sink — no coordination needed. Cancellation propagates everywhere at once through the shared context — which matters because closing alone can't stop a pipeline early: if the sink stops reading, upstream stages just block on full channels. Backpressure is also built in: every stage runs at the pace of the slowest one downstream, because channel sends block. To widen a slow stage, run the worker pool from above as that stage and merge with Merge — the patterns compose.

Bounded parallelism — semaphore channel and errgroup¶

"Fetch these 10,000 URLs, but no more than 20 at a time." When the work is a known collection rather than a stream, you can skip the standing worker pool and bound goroutines directly with a semaphore channel — a buffered channel where the buffer slots are the permits:

sem := make(chan struct{}, 20)
var wg sync.WaitGroup
for _, url := range urls {
    wg.Add(1)
    sem <- struct{}{} // acquire: blocks when 20 are in flight
    go func(url string) {
        defer wg.Done()
        defer func() { <-sem }() // release
        fetch(ctx, url)
    }(url)
}
wg.Wait()

Acquiring before launching the goroutine means at most 20 goroutines ever exist, not 10,000 goroutines of which 20 make progress — a distinction worth being deliberate about. The production version also handles the question that always comes next ("what about errors?"):

g, ctx := errgroup.WithContext(ctx)
g.SetLimit(20)
for _, url := range urls {
    g.Go(func() error {
        return fetch(ctx, url) // first error cancels ctx for all others
    })
}
if err := g.Wait(); err != nil { /* first failure */ }

errgroup.WithContext gives fail-fast semantics for free: the first task to return an error cancels the shared context, every other fetch observes ctx.Done() and unwinds, and Wait returns that first error.

The errgroup implementation is essentially a sync.Once capturing the first error, a cancel invoked on first failure and after Wait — in about fifty lines you no longer have to write, test, or review. That's the real argument for reaching for it: not that the hand-rolled version is impossible, but that its bugs are the silent kind that pass tests and deadlock under load.

Timeout and rate limiting¶

Timeout around any channel wait is a two-case select:

select {
case res := <-resultCh:
    return res, nil
case <-time.After(2 * time.Second):
    return nil, ErrTimeout
}

with the production caveat that for calls that carry a context you'd use context.WithTimeout instead, so the deadline propagates to everything downstream instead of just abandoning the wait. (And in a hot loop, prefer a reused time.Timer — each time.After allocates a timer that isn't collected until it fires.)

A simple rate limiter is a ticker used as a permit stream — receive one tick per allowed operation:

tick := time.NewTicker(time.Second / 100) // 100 ops/sec
defer tick.Stop()
for job := range jobs {
    <-tick.C
    go handle(job)
}

For "allow bursts of B, refill at R per second" — the token bucket — the trick is that a buffered channel is the bucket: capacity B, a goroutine dropping a token in every 1/R seconds (non-blocking send so a full bucket discards the token), workers receiving a token per operation. In production, golang.org/x/time/rate.Limiter implements exactly that with a Wait(ctx) that blocks politely.

Graceful shutdown — putting it together¶

The capstone: a service with producers and a worker pool that, on SIGTERM, stops accepting work, finishes what's in flight, and exits within a deadline. The composition is three ideas you already have. signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM) turns the OS signal into context cancellation. Producers stop on ctx.Done() and close the jobs channel — that's the "stop accepting, finish in-flight" half, because workers ranging over jobs drain it and exit naturally. And the deadline half is a race between completion and a timer:

done := make(chan struct{})
go func() { wg.Wait(); close(done) }()

select {
case <-done: // clean drain
case <-time.After(30 * time.Second): // give up; report what's still running
}

The subtle point: there are two stop signals with different meanings. Closing the jobs channel means "no more input, drain and stop" — graceful. Context cancellation means "stop now, abandon blocking operations" — the hard deadline. A well-shaped worker honors both, which is precisely why the worker-pool code above has both the range exit and the ctx.Done() case. This is also, recognizably, what worker.Run does in the Temporal SDK: stop polling, drain in-flight tasks under a grace period, then force-stop.

Choosing a Pattern: The Decision Path¶

With five patterns on the table, the practical question is which one a given problem calls for. The good news is that the choice is almost fully determined by answering three questions about the work, in order — the pattern falls out at the end.

Question one: is the work a finite collection you hold in your hand, or an open-ended stream? This is the biggest fork. A finite collection — "these 10,000 URLs," "every file in this directory" — wants bounded parallelism: you launch tasks for known items, bound how many run at once, and wait for all of them; there is no standing machinery left afterward. A stream — jobs arriving from a queue, requests from a socket, events from a subscription — wants a worker pool: long-lived workers exist before the work does, and the interesting lifecycle question becomes shutdown, not completion.

Question two (if it's a collection): do you care about errors, and should one failure stop the rest? If yes — the common case in request handling, where there's no point fetching the other 19 shards after one has failed — use errgroup with SetLimit: first error cancels the shared context, Wait hands you that error, five lines total. If failures are independent and you genuinely want everything attempted regardless — best-effort cache warming, sending independent notifications — the plain semaphore channel is enough, and its simplicity is the point: no context plumbing, no error collection you'd ignore anyway. (If you need all errors rather than the first, that's neither: collect results into a pre-sized slice indexed by position — no locking needed, each goroutine writes its own slot — and inspect afterward.)

Question three (if it's a stream): does the work have stages? A single processing step is the worker pool as written. Multiple steps with different costs — parse, then enrich, then write — become a pipeline, because separating stages lets each scale independently: the cheap parse stage stays a single goroutine, the slow enrich stage becomes a worker pool, and fan-in/Merge reassembles the widened stage's outputs into one channel for the next. That composition is the whole reason fan-in exists as a named pattern — you rarely reach for it directly; it arrives when a pipeline stage widens.

Two cross-cutting concerns then overlay whichever pattern you picked. If the constraint is rate rather than concurrency — an API allowing 100 requests per second, regardless of how many are in flight — that's the rate limiter, and note that it composes with rather than replaces the others: a worker pool of 20 can still sit behind a 100 req/s token bucket, because the two limits bound different resources (memory and open connections versus the provider's quota). And if the process serves traffic, graceful shutdown isn't optional garnish — it decides how the jobs channel closes and who waits on what, so it's worth choosing before writing the pool, not bolting on after.

A worked example to make the path concrete: "sync a customer's 50,000 records into a third-party CRM that allows 10 concurrent connections and 50 calls per second." Finite collection → bounded parallelism. Failures should stop the run (an expired credential fails every subsequent call too) → errgroup.WithContext with SetLimit(10). Rate constraint on top → each task takes a token from a rate.Limiter before calling. Three decisions, and the whole design is determined.

If in doubt, default to the simplest shape that answers the questions: errgroup for collections, a worker pool for streams, and add stages, merging, and rate limits only when the problem names them. Premature pipelines are how codebases end up with six channels where one function call would do — concurrency is a cost you pay for throughput or responsiveness, not a style.

The Classic Pitfalls¶

Goroutine leaks are pitfall number one, and every variant has the same anatomy: a goroutine blocked on a channel operation that can never complete. The abandoned sender — a goroutine computing a result for a caller that timed out and went away, blocked forever on an unbuffered send — is the classic; the fix is a buffer of one (send always completes, result gets collected by the garbage collector) or a select with ctx.Done(). The audit habit worth building: for every go statement, name the event that guarantees it exits. If you can't, it leaks.

Channel-close mistakes are pitfall two: closing from the receiver side, closing twice, or sending after close — the last two panic outright. The worker-pool closer pattern (wg.Wait() then a single close) exists to make all three impossible by construction.

WaitGroup misuse — Add inside the spawned goroutine instead of before the go statement — races Add against Wait and lets Wait return early. It passes tests on fast machines and fails in production, which is what makes it so persistent.

Data races on shared variables — the counter incremented from N goroutines without a mutex or atomic — remain the most common concurrency bug in review. The answer includes the tooling: go test -race and go run -race catch these at runtime and belong in CI. Related and subtler: the pre-1.22 loop-variable capture, where every closure sees the last value of the loop variable. Go 1.22 fixed the semantics (each iteration gets a fresh variable), but older codebases still carry both the bug and the v := v workaround, so it's worth knowing both worlds.

Deadlocks round it out: an unbuffered send with no concurrent receiver ("all goroutines are asleep"), two goroutines each waiting on the other, or — the sneaky one — a pipeline where an early-exiting consumer leaves producers blocked on full channels forever. The diagnosis tools: a SIGQUIT (Ctrl-) dump or pprof goroutine profile, which shows every goroutine's blocked-at stack. Ten thousand goroutines parked on the same channel send is a leak announcing itself.

Common Questions, Answered¶

Buffered or unbuffered — how do you choose?¶

Default to unbuffered, because it gives the strongest guarantee: a completed send means the receiver has the value, so the channel synchronizes as well as communicates, and problems show up immediately as blocking instead of hiding in a buffer. Add a buffer for one of three specific reasons: a known small burst you want to absorb (queue semantics with backpressure when it fills), a semaphore where the capacity is the concurrency limit, or a buffer of exactly one so a producer can fire-and-forget a single result without leaking if the consumer disappears. What you shouldn't do is add a buffer to "fix" a deadlock — that usually converts a visible bug into an invisible one that returns under load when the buffer fills.

How do you stop a goroutine from the outside?¶

You can't — Go has no kill primitive, deliberately — so the real answer is that goroutines stop themselves, and your job is to give every goroutine a stop signal it actually observes. The standard signal is a context: every blocking point in the goroutine becomes a select with a case <-ctx.Done() arm, so cancellation wakes it wherever it's parked. For "no more work" rather than "abort," closing the input channel is the gentler signal — a range loop drains and exits. And the discipline that makes it stick: don't write go func() without being able to say which of those two signals guarantees that goroutine's exit.

When a mutex and when a channel?¶

By what you're modeling. If data is moving between goroutines — work items, results, events — a channel, because transferring a value through a channel also transfers ownership, and the happens-before guarantee means no locking at either end. If data is staying put and multiple goroutines touch it — a counter, a cache, a map of live sessions — a mutex, because wrapping shared state in channel choreography means building a server goroutine and request/response protocol to do what two lines of Lock/Unlock do. The working heuristic: channels for communication, mutexes for state — and if a mutex is held across anything that blocks, that's the sign the design wants restructuring.

What are the semantics of a closed channel, exactly?¶

Close is a broadcast from sender to receivers that no more values are coming — and it's the only channel operation that naturally fans out to all receivers, which is why ctx.Done() is implemented as a channel that cancellation closes. Mechanically: receives on a closed channel first drain any buffered values, then return the zero value with ok == false; a range loop exits at that point. Sends on a closed channel panic, closing twice panics — which is why the rule is that only the sender closes, and with multiple senders, only a coordinator that knows all senders are done, typically a goroutine sitting behind a WaitGroup. And channels don't need closing to be collected — close is a signal you send when receivers must know the end arrived, not a resource you must release.

Limit concurrency to N — what are the options?¶

Three, in increasing order of what they give you. A semaphore channel — buffered to N, acquire by sending before launching the goroutine, release by receiving — is the primitive; acquiring before the launch matters because it caps goroutines created, not just goroutines progressing. A fixed worker pool — N long-lived workers ranging over a jobs channel — adds amortization: no per-task goroutine, a natural place for per-worker state, and the shutdown story comes from closing the jobs channel. And errgroup with SetLimit(n) is the production choice for collection-shaped work, because it folds in the two things the first two don't: first-error propagation and cancelling the survivors when one task fails.

Two goroutines increment a counter a million times each and the total comes up short — why?¶

Because counter++ is a read, an add, and a write, and without synchronization the two goroutines interleave those steps and overwrite each other's updates — a data race, which in Go is not just a wrong-count problem but undefined behavior. Three fixes, chosen by context: atomic.AddInt64 (or the atomic.Int64 type) for a bare counter — cheapest by far; a sync.Mutex when the counter is part of a larger invariant that must update atomically with other fields; or restructure so each goroutine owns a local count and the totals merge at the end — no sharing, nothing to race. Either way, go test -race catches this class of bug at runtime and belongs in CI.

How do you add retries and backoff on top of the worker pool?¶

Keep the pool exactly as it is and make retry a policy at the job level, not the pool level. Each job carries an attempt count and a not-before time. A worker that fails a job doesn't loop retrying it in place — that would occupy a worker slot for the full backoff — it computes the next attempt time with exponential backoff plus jitter and hands the job to a scheduler: a goroutine owning a min-heap ordered by ready time, sleeping on a timer until the earliest job is due, then re-sending it to the jobs channel. Jitter matters because a burst of correlated failures otherwise synchronizes into retry waves. Cap attempts and shunt exhausted jobs to a dead-letter destination for humans. The resemblance is worth naming: this is a miniature of what a durable execution engine does — the heap is the timer store, the jobs channel is the task queue, at-least-once delivery means handlers need idempotency — except this one evaporates on restart, which is the pitch for durable timers in one sentence.

Key Takeaways¶

  • Learn the worker pool until you can write it from memory along with its three invariants: bounded workers, dual shutdown paths (input close and context cancel), single sender-side close behind a WaitGroup. Every other pattern here is a rearrangement.
  • Account for exits. The strongest habit in concurrent Go is pointing at each go statement and naming the event that guarantees that goroutine terminates. Leaks hide wherever that question has no answer.
  • Know both layers: build the primitives by hand (semaphore channel, fan-in, token bucket) to understand them, then use the production libraries (errgroup, x/time/rate) and tooling (-race in CI, goroutine dumps for stuck processes) in real code.
  • The patterns aren't academic: a Temporal worker is poller goroutines, a slot semaphore, task channels, and context-driven graceful shutdown — the matching-service article describes the server side of the same machinery.
